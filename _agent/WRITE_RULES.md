# WRITE_RULES

本文件是 `_agent` 目录的写入规范。所有 chat 在建议写入或实际写入 `_agent` 文档前，都应按本文件区分职责、格式和边界，避免内容混淆。

## 总原则

- 先判断内容类型，再选择目标文档；同一条记录可以拆分写入多个文档。
- 事实、决策、任务、模块状态、版本变化、临时想法必须分开记录。
- 记录应服务于跨 chat 接续：其他 chat 只读 `AGENTS.md` 和 `_agent` 目录，也应能理解项目目标、数据结构、模块历史、当前状态、算法思路、待办和后续方向。
- 记录应简洁但完整，保留可追溯线索，不粘贴大段命令输出、完整数据、密钥、`.env` 内容或临时噪声。
- 不确定内容必须标记为“未验证”“推测”或“待确认”，并优先放入 `NOTES.md`。
- 每条记录必须尽量标注状态和来源。状态可使用 `confirmed`、`draft`、`inferred`、`deprecated`；来源可使用“用户确认”“代码检查”“命令输出”“官方文档”“推测”。

## 记录状态与来源

- `confirmed`：用户已确认，或已由代码/命令/文档证据支持。
- `draft`：拟写入内容、草稿方案或尚待用户审核的内容。
- `inferred`：基于文件名、代码结构或上下文推断，但尚未完整验证。
- `deprecated`：已废弃、被替代或不再代表当前状态。
- 记录来源应尽量具体到用户指令、文件路径、命令摘要或官方文档链接。

## 文档职责

### `../AGENTS.md`

只记录 AI agent 必须遵守的长期规则，包括工作方式、写入要求、安全边界和项目特殊约束。

适合写入：

- 所有 chat 都必须遵守的规则。
- 用户明确确认的长期偏好。
- 写入 `_agent` 文档的强制要求。

不适合写入：

- 某次实验的细节。
- 普通待办。
- 模块版本细节。
- 未验证的算法想法。

### `WRITE_RULES.md`

只记录 `_agent` 文档系统本身的职责划分、写入格式和写入边界。

适合写入：

- 各文档分别记录什么。
- 统一记录模板。
- 多文档联动规则。
- 禁止写入的内容类型。

不适合写入：

- 具体项目实验结论。
- 具体代码模块状态。
- 普通任务进度。

### `README.md`

记录 `_agent` 目录的入口说明和文件索引，帮助新 chat 快速知道应该读哪些文件。

适合写入：

- `_agent` 目录目的。
- 文件列表和一句话职责。
- 推荐阅读顺序。

不适合写入：

- 详细写入规范。
- 模块实现细节。
- 长篇历史记录。

### `PROJECT_STRUCTURE.md`

记录完整项目树、根目录文件、代码文件、同源最高级目录来源与作用、最低级非代码目录内容与统计，以及数据库目录边界。所有写入必须先遵守 `PROJECT_STRUCTURE.md` 开头“永不可更改的写入规则”。

适合写入：

- 遍历项目目录后发现的新增、删除或尚未记录的路径。
- 全部目录的树状结构，以及同源最高级目录的来源、作用和直属子文件夹成分。
- 项目根目录文件和代码文件的逐文件路径、作用、来源与最后手动更新时间。
- 最低级非代码目录及父目录 `[本级文件]` 的内容说明、文件数和文件类别。
- 以数据库为最小单位的目录路径、来源、作用、子文件夹成分、文件数和文件类别；数据库内部文件不得逐项展开。
- 无可靠依据时留空的作用或来源字段。

不适合写入：

- 算法细节。
- 任务进度。
- 决策原因。
- 数据库内部逐文件清单。
- 未经检查的用途或来源猜测。

格式规则：

- 默认使用 Markdown 树状列表和结构化表格：目录树负责表达层级，表格负责逐文件记录、叶目录统计和数据库汇总。
- Markdown 无法同时保证完整性、可读性和稳定机器解析时，可改用其他既方便人类阅读、又方便 GPT/Codex 读写的文本格式；格式迁移仍须先展示草稿并取得用户确认。
- 超大更新不在 chat 中粘贴完整 diff；按 `AGENTS.md` 的 diff/review 规则展示统计、关键片段和完整性校验。

### `TODO.md`

记录明确可执行的任务、状态和下一步。

适合写入：

- 待做、进行中、已完成任务。
- 每项任务的优先级、涉及文件、阻塞点和下一步。
- 用户明确提出但尚未完成的要求。

不适合写入：

- 长篇算法解释。
- 已经定案的架构原因。
- 模糊想法，除非转化为明确行动项。

建议格式：

```md
- [ ] 优先级：任务标题
  - 日期：
  - 用户需求：
  - 涉及文件/模块：
  - 当前状态：
  - 阻塞点：
  - 下一步：
```

### `NOTES.md`

记录临时笔记、调研过程、观察、推测、风险和可能改进思路。

适合写入：

- 未验证的算法想法。
- 调试观察和实验线索。
- 需要稍后确认的假设。
- 设计备选方案的早期思考。

不适合写入：

- 已经确认的长期规则。
- 已经做出的正式决策。
- 可直接执行的任务清单。

建议格式：

```md
### 日期：主题

- 类型：观察/推测/风险/改进想法
- 涉及文件/模块：
- 内容摘要：
- 证据或线索：
- 待验证问题：
- 可能下一步：
```

### `MODULES.md`

记录项目各模块的用途、输入输出、历史版本、当前最新版本、已实现内容、待实现内容、算法思路和改进方向。

适合写入：

- 模块职责和边界。
- 版本历史及每次更新目的。
- 最新可用脚本或模型。
- 输入数据、输出结果和关键参数。
- 已实现/待实现功能。
- 算法思路和可改进方向。

不适合写入：

- 单次会话闲聊。
- 与模块无关的协作规则。
- 没有归属模块的临时想法。

建议格式：

```md
### 模块名称

- 当前最新版本：
- 相关文件：
- 模块用途：
- 输入：
- 输出：
- 已实现内容：
- 待实现内容：
- 历史版本与更新目的：
- 算法思路：
- 可能改进方向：
- 验证状态：
- 后续建议：
```

### `CHANGELOG.md`

记录已经发生的重要项目变更，按时间组织。

适合写入：

- 新增、修改、删除的重要文件。
- 代码行为变化。
- 文档结构变化。
- 重要实验流程变化。

不适合写入：

- 尚未发生的计划。
- 未验证想法。
- 长篇原因解释；原因应写入 `docs/decision-log.md`。

建议格式：

```md
## 日期

- 变更：
- 涉及文件/模块：
- 更新目的：
- 影响：
- 验证状态：
```

### `ROADMAP.md`

记录中长期目标、里程碑和未来方向。

适合写入：

- 阶段性目标。
- 里程碑。
- 中长期算法或工程方向。
- 尚未拆成具体任务的大方向。

不适合写入：

- 当前小任务。
- 已完成的变更记录。
- 具体模块版本细节。

### `CONTRIBUTING.md`

记录协作流程、开发约定、测试要求、提交规范和代码审查标准。

适合写入：

- 如何运行测试。
- 分支、提交、PR 或文件命名规范。
- 代码风格和验证要求。
- 多人或多 chat 协作流程。

不适合写入：

- 项目算法细节。
- 临时任务清单。
- 实验结论。

### `docs/decision-log.md`

记录已经定案的重要决策，尤其是以后可能被追问“为什么这么做”的内容。

适合写入：

- 文档结构决策。
- 技术路线选择。
- 算法方案取舍。
- 数据处理策略。
- 废弃某个方案的原因。

不适合写入：

- 未定论想法。
- 普通变更流水账。
- 具体待办列表。

建议格式：

```md
## 日期：决策标题

- 背景：
- 用户需求：
- 决策：
- 备选方案：
- 决策原因：
- 影响范围：
- 后续追踪：
```

## 多文档联动规则

- 用户提出长期规则：写入根目录 `AGENTS.md`；如果涉及文档系统本身，也写入或更新 `WRITE_RULES.md`。
- 新增或改变 `_agent` 文件职责：更新 `WRITE_RULES.md` 和 `README.md`，必要时写入 `docs/decision-log.md`。
- 出现明确任务：写入 `TODO.md`；任务完成后更新状态，并可在 `CHANGELOG.md` 记录结果。
- 发生代码或模块更新：更新 `CHANGELOG.md`；如果影响模块状态，同时更新 `MODULES.md`；如果涉及技术取舍，同时更新 `docs/decision-log.md`。
- 出现未验证思路或风险：先写入 `NOTES.md`；验证后再迁移到 `MODULES.md`、`TODO.md` 或 `docs/decision-log.md`。
- 形成中长期方向：写入 `ROADMAP.md`；拆成具体任务后同步到 `TODO.md`。
- 项目文件结构发生变化或需要补充说明：更新 `PROJECT_STRUCTURE.md`，并严格遵守其开头不可更改规则以及本文定义的完整树、逐文件、叶目录和数据库边界。

## 每次会话后的建议格式

每次回答结束时，如有值得沉淀的内容，应主动向用户提出可写入 `_agent` 的建议，并询问是否添加。建议格式如下：

```md
建议写入：

1. 目标文档：`_agent/...`
   - 日期：
   - 状态：
   - 来源：
   - 用户需求：
   - 涉及文件/模块：
   - 已完成内容：
   - 未完成内容：
   - 验证状态：
   - 后续建议：
```

## 禁止写入

- 密钥、账号、token、`.env` 真实内容。
- 大段原始数据或不可公开数据。
- 大段命令输出，除非经过摘要并有明确必要。
- 与项目无关的闲聊。
- 没有标注来源和状态的猜测性结论。
- 会误导其他 chat 的过期状态；如果状态变化，必须更新或标记废弃。

## 补充规则：handoff 归档与职责迁移

来源：用户要求、现有 `_agent/WRITE_RULES.md`、本次 handoff 拆分需求  
最后手动更新时间：2026-06-23

### `PROJECT_HANDOFF.md`

`PROJECT_HANDOFF.md` 只适合作为临时总交接文件或跨 chat 转移文件。完成拆分后，不应继续作为主要维护文件。

适合写入：

- 从其他 chat 转移来的完整原始交接内容。
- 尚未拆分进职责文档的临时总览。
- 明确标注状态、来源和最后手动更新时间的迁移材料。

不适合写入：

- 已经拆分进 `MODULES.md`、`TODO.md`、`ROADMAP.md`、`NOTES.md` 或 `docs/decision-log.md` 的长期内容。
- 新增模块状态。
- 新增待办。
- 新增决策。
- 新增实验结论。

### `_agent/arc/`

`_agent/arc/` 用于归档不再作为当前维护入口、但仍需要保留历史追溯价值的 `_agent` 文档。

适合写入：

- 已拆分完成的 handoff 文件。
- 旧版交接文件。
- 用户明确要求归档的项目记录文件。

不适合写入：

- 当前仍在维护的模块状态。
- 当前 TODO。
- 当前决策。
- 未经拆分整理的长期主线记录。

### Handoff 拆分规则

当 `PROJECT_HANDOFF.md` 中的信息需要长期保留时，应按以下边界拆分：

| 内容类型 | 目标文档 |
|---|---|
| 模块、脚本、函数、算法、输入输出、状态 | `MODULES.md` |
| 未完成事项、阻塞点、下一步 | `TODO.md` |
| 中长期路线、阶段目标、路线演化 | `ROADMAP.md` |
| 观察、风险、用户偏好、推测 | `NOTES.md` |
| 已定案技术取舍和原因 | `docs/decision-log.md` |
| 完整项目树、根目录/代码文件清单、目录来源与作用、叶目录统计、数据库边界和最后手动更新时间 | `PROJECT_STRUCTURE.md` |
| 文档系统入口和阅读顺序 | `README.md` |
| 已发生的重要变更 | `CHANGELOG.md` |
| `_agent` 写入规则变化 | `WRITE_RULES.md` |

### 冲突处理规则

如果归档 handoff 与已拆分文档发生冲突：

1. 优先以最新用户明确确认内容为准。
2. 若 `PROJECT_HANDOFF.md` 内部有新旧冲突，以其更新、更明确、状态为 `confirmed` 的章节为准。
3. 当前 `PROJECT_HANDOFF.md` 中第 0 节优先于旧章节。
4. 如果无法判断，应在 `NOTES.md` 标注为待确认，不应直接写入 `MODULES.md` 或 `docs/decision-log.md` 作为 confirmed 事实。

### 归档后维护规则

- `PROJECT_HANDOFF.md` 归档后，后续 chat 不应继续向其追加内容。
- 需要新增项目记录时，应根据内容类型写入对应职责文档。
- 引用归档内容时，应写明来源为 `_agent/arc/PROJECT_HANDOFF.md`。
- 若未来再次从其他 chat 导入大型 handoff，应先放入临时 handoff 文件，审核后再拆分归档。
